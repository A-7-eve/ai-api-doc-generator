## 1. 项目背景与目标

### 1.1 背景

在软件开发中，接口文档是前后端协作的核心纽带。然而传统接口文档维护存在以下痛点：

- **手写文档耗时**：开发者需要手动编写每个接口的描述、参数说明、示例数据，效率低
- **文档与代码不同步**：代码变更后文档忘记更新，导致文档过时、误导调用方
- **Swagger 等注解方案语义不足**：能提取 URL、参数类型，但缺少自然语言描述、示例数据、边界场景说明
- **新人理解成本高**：干瘪的参数列表无法帮助新成员快速理解接口用途和使用方式

### 1.2 项目目标

构建一个 AI 辅助的接口文档自动生成系统，能够：

1. **自动解析** Java/SpringBoot 项目的 Controller 代码，提取接口元数据（URL、HTTP 方法、参数、返回类型、注释）
2. **AI 增强**：调用云端大模型，为每个接口自动生成自然语言描述、参数说明、请求/响应示例、边界场景提示
3. **多格式输出**：生成 OpenAPI 3.0 JSON 和 Markdown 格式的接口文档
4. **在线浏览与编辑**：提供 Web 界面，支持在线查看、人工编辑修正、一键导出

### 1.3 核心价值

| 传统 Swagger | 本系统 |
|-------------|--------|
| 从注解提取 URL/参数名 | 从代码 AST 提取 + AI 补语义 |
| 描述靠 `@ApiOperation` 手写 | AI 自动生成描述 |
| 示例数据需手填 | AI 自动生成示例 |
| 无边界场景提示 | AI 提示异常输入和错误码 |
| 文档与代码半同步 | 每次解析即最新代码状态 |

### 1.4 项目特色与创新点

1. **AI 语义增强**：不止提取代码结构，还用大模型补自然语言描述、示例数据、边界场景，这是相比 Swagger 的核心差异
2. **边界场景自动提示**：结合测试思维，AI 自动列出可能的异常输入和错误码，降低接口测试遗漏风险
3. **降级容错设计**：大模型不可用时自动降级为纯解析结果，系统仍能正常运行，保证可用性
4. **多格式导出**：OpenAPI JSON 可被 Swagger UI/Apifox 直接加载，Markdown 便于人工阅读和 Git 管理
5. **代码 AST 解析 + 正则兜底**：javalang 解析失败时自动切换正则，提高复杂代码兼容性
6. **用户角色与权限体系**（v2.1）：JWT 登录鉴权、项目归属隔离、管理员用户管理，让系统具备多用户生产化特征（v2.0 的 54 条测试增至 78 条）
7. **多页面 SPA 架构**（v2.2）：Vue Router 拆分 4 个独立业务页面（登录/工作台/项目历史/导出中心/用户管理），路由懒加载 + 登录与角色双重守卫，侧边导航布局，符合前后端分离工程的完整交互形态

## 5. 详细设计

### 5.1 代码解析层详细设计（v2.4 升级为多语言引擎架构）

#### 5.1.0 多语言引擎注册表与分发器（v2.4 新增）

v2.4 引入引擎注册表（parser/engine_registry.py）与分发器（parser/dispatcher.py），解析层从单一 Java 引擎升级为多语言引擎架构：

| 引擎 | 语言 | 技术方案 | 语法版本范围 |
|------|------|---------|-------------|
| javalang-ast v1.0 | Java | javalang AST + 正则降级 | Java 8~17（Spring MVC 4.x/5.x/6.x 注解） |
| python-ast v1.0 | Python | 内置 ast 模块 + 正则降级 | Python 3.0~3.12（FastAPI/Flask 装饰器路由） |
| c-regex v1.0 | C | 纯正则提取 | ANSI C (C89)/C99/C11 函数定义风格 |

分发流程：上传 ZIP/路径 → 按扩展名统计语言（.java/.py/.c/.h）→ 逐语言调用对应引擎 → 合并 ProjectMeta（languages + engineInfo 标注）。

**版本管理落地**：每个引擎在注册表中声明 syntax_versions（支持的语法版本范围）；遇到解析器无法处理的语言版本（如 3.12+ 新语法在旧解释器上 ast.parse 抛 SyntaxError）时自动降级为正则模式，degraded 状态记入 engineInfo，解析不中断。

**C 语言定位说明**：C 语言没有路由注解体系，无法直接映射 HTTP 语义，C 引擎定位为"API 函数清单"（method 统一 POST、路径=函数名、static 内部函数跳过）；C 项目导出 Markdown 完整可用，OpenAPI 的 paths 为空。

#### 5.1.1 解析流程（Java 引擎，javalang-ast）

```
输入: Java项目路径(ZIP或文件夹)
    │
    ▼
1. 遍历项目目录，找到所有 .java 文件
    │
    ▼
2. 对每个 .java 文件:
    a. 用 javalang 解析为 AST
    b. 检查类注解是否含 @RestController 或 @Controller
    c. 若是 Controller:
       - 提取类级 @RequestMapping → baseUrl
       - 遍历类中每个方法:
         * 检查方法注解 @GetMapping/@PostMapping 等
         * 提取 HTTP method + path
         * 提取方法参数列表 + 参数注解
         * 提取返回类型
         * 提取注释
    d. 若是 DTO/Entity 类:
       - 提取字段名、类型、注解(如 @NotNull)
    │
    ▼
3. 组装为结构化元数据 (List[ControllerMeta])
    │
    ▼
输出: JSON 格式的元数据
```

#### 5.1.2 关键解析逻辑（Java）

**提取 Controller 类映射注解：**

| 注解类型 | HTTP Method | 提取规则 |
|----------|------------|---------|
| @GetMapping | GET | value/path 属性 → 路径 |
| @PostMapping | POST | value/path 属性 → 路径 |
| @PutMapping | PUT | value/path 属性 → 路径 |
| @DeleteMapping | DELETE | value/path 属性 → 路径 |
| @RequestMapping | 多态 | method 属性决定 HTTP 方法 |

**提取参数注解：**

| 注解类型 | 参数来源 | 提取规则 |
|---------|---------|---------|
| @RequestParam | Query 参数 | name/value → 参数名, required → 是否必填 |
| @PathVariable | Path 参数 | name/value → 参数名 |
| @RequestBody | Body 参数 | 类型 → DTO 类名 |
| 无注解 | 简单类型 | 直接取参数名和类型 |

#### 5.1.2a Python 引擎解析规则（python-ast，v2.4 新增）

**路由装饰器识别：**

| 装饰器形态 | 框架 | 提取规则 |
|-----------|------|---------|
| @app.get("/path") / @router.post("/path") | FastAPI | 装饰器名→HTTP 方法，首参字符串→路径 |
| @app.get/@app.post 等快捷方式 | Flask 2.0+ | 同上 |
| @app.route("/path", methods=["POST"]) | Flask | methods 首元素→HTTP 方法，缺省 GET |

**参数提取**：带类型注解的形参生成 ParamMeta（self/cls/request/db 等跳过）；类型名以 Schema/Create/Update 结尾或为 Body/Payload → 标记 @RequestBody；docstring 作为接口注释；无路由装饰器的函数忽略；tests/venv/__pycache__ 目录跳过。

**降级策略**：ast.parse 抛 SyntaxError（语法过新/过旧/损坏）时自动降级正则提取（@xxx.get("路径") 后 1~3 行内的 def），Controller 注释标记"正则兜底解析"。

#### 5.1.2b C 引擎解析规则（c-regex，v2.4 新增）

- 函数定义/声明均收录（`{` 定义与 `;` 声明），static 函数跳过
- 预处理阶段剥离块注释与字符串字面量（防止注释里的伪函数原型误匹配），保持行号对齐
- 参数解析支持 const/指针修饰（如 `const char* name` → type=const char*）；复杂签名（函数指针）按整体类型处理
- 函数体上方 // 或 /* */ 注释提取为接口说明，文件头 /** */ 注释提取为 Controller 说明

#### 5.1.3 容错策略

| 异常场景 | 处理方式 |
|---------|---------|
| javalang 解析失败 | 降级为正则匹配提取类名、方法名、注解 |
| 注解属性缺失 | 使用方法名作为默认 path |
| 注释缺失 | 标记为 "无注释"，交由 AI 生成 |
| DTO 类找不到 | 生成空示例，标注 "未找到 DTO 定义" |
| 无类级 @RequestMapping | baseUrl 设为空字符串，直接使用方法级完整路径（如 petclinic 的 `/owners/new`） |
| @Controller + @ResponseBody | 兼容非 @RestController 写法，检测方法级 @ResponseBody 判断是否返回 JSON |

### 7.1 Pydantic 数据模型定义

```python
# models/schemas.py

from pydantic import BaseModel
from typing import Optional
from enum import Enum


class HTTPMethod(str, Enum):
    GET = "GET"
    POST = "POST"
    PUT = "PUT"
    DELETE = "DELETE"
    PATCH = "PATCH"


class ParamMeta(BaseModel):
    """参数元数据"""
    name: str
    type: str
    annotation: Optional[str] = None       # @RequestParam / @PathVariable / @RequestBody
    required: bool = True
    # AI 增强字段
    description: Optional[str] = None
    example: Optional[str] = None


class EndpointMeta(BaseModel):
    """接口元数据"""
    endpointId: Optional[str] = None
    method: HTTPMethod
    path: str
    fullPath: str
    javaMethod: str
    returnType: Optional[str] = None
    comment: Optional[str] = None
    sourceCode: Optional[str] = None
    params: list[ParamMeta] = []
    # AI 增强字段
    description: Optional[str] = None
    requestExample: Optional[str] = None
    responseExample: Optional[str] = None
    edgeCases: list[str] = []
    errorCodes: list[dict] = []


class ControllerMeta(BaseModel):
    """Controller 元数据"""
    controllerId: Optional[str] = None
    className: str
    baseUrl: str
    packageName: Optional[str] = None
    comment: Optional[str] = None
    endpoints: list[EndpointMeta] = []


class DtoFieldMeta(BaseModel):
    """DTO 字段元数据"""
    name: str
    type: str
    annotations: list[str] = []     # @NotNull / @Size 等


class DtoMeta(BaseModel):
    """DTO 类元数据"""
    className: str
    fields: list[DtoFieldMeta] = []


class ProjectMeta(BaseModel):
    """项目元数据"""
    projectId: Optional[str] = None
    projectName: str
    controllers: list[ControllerMeta] = []
    dtos: list[DtoMeta] = []
    parseTime: Optional[str] = None
    # 归属信息（v2.1 角色功能）
    ownerUserId: Optional[str] = None
    ownerName: Optional[str] = None


class AIEnhancement(BaseModel):
    """AI 增强结果"""
    description: str
    params: list[dict] = []
    requestExample: str = ""
    responseExample: str = ""
    edgeCases: list[str] = []
    errorCodes: list[dict] = []


# v2.1 用户与鉴权模型
class UserMeta(BaseModel):
    userId: str
    username: str
    role: str = "user"          # "admin" | "user"
    createdAt: Optional[str] = None


class TokenResponse(BaseModel):
    token: str
    tokenType: str = "Bearer"
    user: UserMeta
```

## 8. AI增强设计

### 8.1 增强策略

```
策略: 逐接口增强 + 批量并发

1. 解析层产出所有接口元数据后
2. 对每个接口并发调用大模型 API (asyncio.gather)
3. 每个接口独立增强, 互不阻塞
4. 单接口失败不影响其他接口
5. 全部完成后合并到 ProjectMeta
```

### 8.2 降级策略

| 场景 | 降级方案 |
|------|---------|
| 大模型 API 超时 | 保留纯解析结果，description 用方法名推演 |
| 大模型返回非 JSON | 用正则提取 JSON 片段；若仍失败，仅保留 description 文本 |
| 大模型 API Key 无效 | 全部接口使用纯解析结果，前端标注"AI增强不可用" |
| 网络断开 | 同上 |

### 8.3 并发控制

```python
# 伪代码
SEM = asyncio.Semaphore(5)  # 最多5个并发请求

async def enhance_all(endpoints: list[EndpointMeta]):
    tasks = [enhance_one(ep) for ep in endpoints]
    return await asyncio.gather(*tasks, return_exceptions=True)

async def enhance_one(endpoint: EndpointMeta):
    async with SEM:
        prompt = build_prompt(endpoint)
        result = await call_llm_api(prompt)
        merge(endpoint, result)
```

### 8.4 Prompt 工程要点

| 要点 | 说明 |
|------|------|
| 强制 JSON 输出 | 系统提示明确要求返回 JSON，拒绝其他文本 |
| 代码上下文 | 将方法源码片段包含在 prompt 中，帮助模型理解逻辑 |
| 参数类型传递 | 传入参数名和类型，让 AI 补充语义 |
| DTO 上下文 | 如果参数是 @RequestBody，传入 DTO 类的字段定义 |
| 少样本示例 | 在 prompt 中给出一个标准输出示例 |
| 温度参数 | temperature=0.3，保证输出稳定性 |
